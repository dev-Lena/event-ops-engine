# 공통 품질 기준 (프로젝트와 관계없이 적용)

어느 프로젝트든 **기본으로** 갖춰야 하는 품질 기준이다. 기능 요구사항에 적혀 있지 않아도 구현한다.
이 문서는 프로젝트 이름 · 기술에 기대지 않게 쓴다 — 다른 프로젝트에 그대로 복사해 쓸 수 있도록.
프로젝트별 수치(한도 · 위치 등)는 각 프로젝트 문서에 적고, 여기에는 기준과 기본값만 둔다.

| # | 기준 | 적용 대상 |
|---|---|---|
| 1 | [글자 수 표시](#1-글자-수-표시) | 글자 수 제한이 있는 모든 텍스트 입력 |
| 2 | [짧은 시간 반복 요청 막기](#2-짧은-시간-반복-요청-막기-rate-limit) | 서버가 받는 모든 요청 |

## 1. 글자 수 표시

글자 수 제한이 있는 입력칸은 **지금 몇 자를 썼고 최대 몇 자인지**를 늘 보여준다. 예: `5/20`

- **언제**: 제한이 있으면 처음부터 늘 보인다 (`0/20`). 입력 중에도 바로 바뀐다.
- **예외**: 사람이 사실상 닿지 않는 **기술적 상한**(이메일 254자, 비밀번호 72자처럼 표준 · 외부 서비스가 정한 값)은 제한만 두고 표시하지 않는다 — 숫자가 오히려 헷갈린다. 표시 여부는 필드 규칙(code-standards.md 2-1)에 적는다.
- **어디**: 입력칸 바로 아래 오른쪽. 왼쪽의 안내 · 오류 문구와 같은 줄에 두어 화면이 밀리지 않게 한다.
- **모양**: 안내 문구와 같은 크기 · 색(보조 글자색), 숫자는 폭이 같은 숫자(tabular-nums)로 — 숫자가 바뀔 때 글자가 흔들리지 않게.
- **세는 단위 = 제한하는 단위**: 화면에 보이는 숫자와 실제 제한(`maxLength`, 서버 검증)이 같은 방식으로 세어야 한다. 웹의 `maxLength`는 UTF-16 길이(`String.length`)로 센다 — 한글 한 글자는 1, 일부 이모지는 2. 다르게 세면 "19/20인데 더 안 써진다" 같은 어긋남이 생긴다.
- **최대에 닿으면**: 더 입력되지 않게 막는다(`maxLength`). 붙여넣기로 넘친 부분은 잘린다. 오류로 막지 않는다 — 이미 쓴 것을 지우게 만들지 않기 위해.
- **최소 글자 수**가 있으면 안내 문구로 알려주고(예: "2자 이상"), 부족하면 칸을 벗어날 때 오류로 알려준다. 카운터는 최대만 보여준다.
- **스크린리더**: 카운터를 입력칸 설명(`aria-describedby`)에 연결해, 칸에 들어갔을 때 함께 읽히게 한다. 한 글자마다 읽어 주지는 않는다(`aria-live` 쓰지 않음) — 입력을 방해하므로.
- **서버도 같은 제한을 검증한다.** 화면의 제한은 편의일 뿐이다.
- 구현: 입력칸 공통 컴포넌트가 `maxLength`만 받으면 자동으로 카운터를 그리게 한다 — 화면마다 따로 붙이다 빠뜨리지 않게.

## 2. 짧은 시간 반복 요청 막기 (rate limit)

서버가 받는 모든 요청에 **사용자(또는 IP)별 짧은 시간 요청 수 제한**을 둔다. 버튼 연타 · 무한 재시도 코드 · 자동화된 반복 호출로 서버 비용 · 외부 API 비용(LLM, 메일 발송 등)이 새는 것을 막는다.

### 원칙

- **누구 기준으로 세나**: 로그인한 요청은 **사용자 ID**, 로그인 전 요청은 **IP**. IP는 통신사 · 회사 망에서 여러 사람이 같이 쓰므로 IP 기준 한도는 넉넉하게 둔다. 이메일 · 개인정보를 키로 쓰지 않는다.
- **요청 종류별로 등급을 나눈다**: 비용이 큰 요청일수록 좁게.
- **넘으면**: HTTP `429 Too Many Requests` + `Retry-After`(초) 헤더 + 내부 사정을 드러내지 않는 오류 코드(예: `{"error":"rate_limited"}`).
- **화면은**: "요청이 많아요. 잠시 후 다시 시도해주세요." 같은 안내를 보여주고, `Retry-After` 동안 버튼을 막는다. 자동 재시도는 하지 않거나, 한다면 간격을 늘려 가며(지수 백오프) 최대 횟수를 둔다.
- **화면에서 먼저 줄인다**: 요청 중에는 버튼을 막고(중복 제출 방지), 입력할 때마다 보내는 검색은 멈춘 뒤 보낸다(디바운스, 기본 300ms).
- **제한은 서버에서** 한다. 화면의 막기는 편의일 뿐, 요청은 화면을 거치지 않고도 올 수 있다.
- **짧은 시간 제한과 별개로 하루 한도**를 둔다: 비용이 드는 외부 호출(LLM 등)은 사용자별 하루 한도와 서비스 전체 하루 한도를 따로 둔다 — 짧은 시간 제한만으로는 천천히 오래 새는 것을 못 막는다.
- **기록한다**: 429가 난 횟수를 로그 · 지표로 남겨, 한도가 너무 좁거나(정상 사용자가 막힘) 공격이 있는지 본다.
- 여러 지역 서버에서 세는 제한(예: Cloudflare Workers Rate Limiting)은 **정확한 계산이 아니다** — 과도한 반복을 끊는 용도로 쓰고, 정확히 세야 하는 것(하루 한도 · 결제)은 DB로 센다.

### 기본 등급 (프로젝트에서 수치를 정하지 않았으면 이 값을 쓴다)

| 등급 | 예 | 기준 | 한도 | 이유 |
|---|---|---|---|---|
| A. 비용이 큰 요청 | LLM 생성, 메일 · 문자 발송, 결제 | 사용자 | **60초에 3회** | 정상 사용은 한 번, 실패 후 다시 시도 1~2번까지만 허용 |
| B. 쓰기 | 저장 · 수정 · 삭제 · 기록 | 사용자 | **60초에 20회** | 사람이 누르는 속도로는 넘기 어렵고, 반복 코드 · 연타는 막힘 |
| C. 읽기 · 일반 | 조회, 검색 자동완성 | 사용자 | **10초에 30회** | 화면 하나를 열 때 병렬 요청 · 검색 입력(디바운스 후)까지 여유 |
| D. 로그인 전 공개 요청 | 로그인 · 가입 전 API, 공개 링크 | IP | **60초에 30회** | 같은 IP를 여러 사람이 쓰는 경우를 고려해 넉넉하게 |

- 인증(로그인 · 가입 · 비밀번호 재설정)처럼 외부 서비스가 이미 제한하는 요청은 그 서비스의 제한을 확인하고 기록한다 (중복으로 더 좁히지 않는다).
- 수치를 바꾸면 이유와 함께 프로젝트 문서에 적는다.
