# 코드 기준 — 재사용 · 모듈화 · 테스트 가능 · 클린 코드

디자인은 달라도 **비슷한 흐름**(온보딩 · 가입 · 마이페이지 · 설정 · 검색 시트 등)을 다른 웹사이트에서 다시 만들 때,
화면을 새로 짜지 않고 **모양(토큰 · 문구)과 설정만 바꿔** 쓸 수 있게 만든다. 프로젝트 이름 · 기술에 기대지 않게 쓴다.

## 1. 계층과 의존 방향

위에서 아래로만 가져다 쓴다. 아래 계층은 위 계층을 모른다.

| 계층 | 담는 것 | 알아도 되는 것 | 몰라야 하는 것 |
|---|---|---|---|
| **screens / features** | 화면 하나 · 기능 하나를 조립 (문구 연결, 저장소 · 서비스 호출, 이동) | 아래 전부 | — |
| **patterns** | 여러 화면에서 반복되는 흐름 컴포넌트 (단계형 폼 틀, 검색 시트, 확인 목록, 새 비밀번호 칸 묶음) | ui · lib | 특정 앱의 저장소 · 주소 · 문구 키 · 외부 서비스 |
| **ui** | 디자인 시스템 기본 부품 (버튼, 입력칸, 선택 칸, 체크박스, 시트, 토스트) | 디자인 토큰 | 문구 라이브러리(i18n), 저장소, 서비스, 라우터 |
| **services** | 외부 서비스 호출 (인증, DB, 결제, LLM) — 결과를 앱이 쓰는 모양 · 오류 키로 바꿔 돌려준다 | lib | 화면 · 컴포넌트 |
| **lib** | 순수 규칙 · 계산 (검증, 변환, 날짜, 점수, 검색) | 다른 lib | React · 브라우저 · 서비스 |

- 화면이 외부 SDK를 **직접 부르지 않는다.** 서비스 모듈을 거친다 → 서비스를 바꾸거나(예: 인증 제공자 교체) 테스트에서 가짜로 바꾸기 쉽다.
- ui · patterns는 **문구를 props로 받는다.** 컴포넌트 안에 문구를 고정하지 않는다 → 언어 · 브랜드가 달라도 그대로 쓴다.
- patterns는 **설정(config)으로 동작**한다. 예: 단계형 흐름은 단계 목록 · 각 단계 완료 조건 · 다음 주소를 데이터로 받는다. 순서를 바꿔도 코드를 고치지 않는다.
- 앱 전용 연결(어느 저장소 · 어느 주소)은 screens에서, 또는 patterns를 감싼 얇은 앱 전용 컴포넌트에서 한다.

## 2. 디자인이 달라도 재사용되게

- **색 · 크기 · 모서리 · 그림자는 디자인 토큰**(CSS 변수 · 테마)으로. 컴포넌트 안에 색 코드(`#cdb9ff`, `rgb(...)`)를 직접 쓰지 않는다 → 새 디자인은 토큰 파일만 바꾼다.
- 한 가지 모양만 필요해도 **변형(variant) · 크기(size) props**로 열어 둔다. 단, 쓰지 않는 옵션을 미리 만들지는 않는다.
- 같은 동작을 두 곳에서 따로 만들지 않는다 (예: 모달 · 시트의 포커스 가두기 · Esc 닫기 → 시트 기본 부품 하나).
- 브라우저 기본 요소(`button`, `input`, `select`, `dialog`)를 먼저 쓴다 → 접근성 · 모바일 동작이 기본으로 따라온다.

## 2-1. 입력 제한은 한 곳에서 정의한다 (필드 규칙)

글자가 들어가는 입력값의 **최소 · 최대 글자 수, 형식, 글자 수 표시 여부**를 필드 규칙 한 곳(예: `field-rules.ts`)에 모은다.
화면(입력칸 `maxLength` · 글자 수 표시 · 안내 문구), 검증 함수, 서버 검증이 **모두 같은 규칙을 가져다 쓴다.**

```ts
export const FIELD_RULES = {
  name: { min: 2, max: 20, counter: true },       // 사람이 부딪히는 제한 → 글자 수 표시
  email: { max: 254, counter: false },            // 표준(RFC 5321) 최대, 형식 검증
  password: { min: 8, max: 72, counter: false },  // 인증 서비스 제한과 같게
  verificationCode: { length: 6 },
} as const;
```

- 다른 프로젝트에서는 **이 파일의 값만 바꿔** 같은 화면 · 검증을 재사용한다.
- 숫자를 화면 · 테스트 · 서버에 따로 적지 않는다 — 한 곳이 바뀌면 나머지가 어긋난다.
- 규칙마다 **왜 그 값인지**(기획 · 표준 · 외부 서비스 제한)를 주석으로 남긴다.
- 글자 수 표시(`5/20`)는 [quality-standards.md](quality-standards.md) 1번을 따른다. 사람이 부딪히는 제한이면 표시하고, 기술적 상한(이메일 254자처럼 사실상 닿지 않는 값)은 표시하지 않는다.

## 3. 테스트할 수 있게

| 대상 | 테스트 | 어떻게 테스트 가능하게 만드나 |
|---|---|---|
| lib (규칙 · 계산) | 단위 테스트 (필수) | 순수 함수. 현재 시각 · 난수는 인자로 받는다 (`today = new Date()` 기본값) |
| services | 단위 테스트 (외부 응답 가짜로) | SDK 호출과 결과 변환 · 오류 키 매핑을 분리 |
| ui · patterns | 컴포넌트 테스트 (상태별: 기본 · 선택 · 비활성 · 오류) | props만으로 모든 상태를 그릴 수 있게 |
| screens | E2E (핵심 흐름) | 외부 서비스는 네트워크 단에서 가짜 응답 |

- **테스트하기 어려우면 구조 문제로 본다.** 숨은 전역 상태, 화면 안의 SDK 직접 호출, 컴포넌트 안에서 `new Date()` 등이 원인인 경우가 많다.
- 테스트 이름은 **무엇을 보장하는지** 문장으로 쓴다 (예: "연 · 월을 바꿔 없는 날이 되면 날을 비운다").

## 4. 클린 코드

- **한 파일 · 한 함수 · 한 책임.** 화면 파일이 200줄을 넘거나 역할이 셋 이상이면 나눌 때가 됐다는 신호다.
- **이름으로 의도를 말한다.** 약어 · 한 글자 이름을 피하고, boolean은 `is/has/can`으로.
- **중복은 세 번째에 추출한다** (rule of three). 두 번까지는 복사가 섣부른 추상화보다 낫다. 단, 규칙 · 검증처럼 **어긋나면 버그가 되는 것은 두 번째부터** 한 곳으로 모은다.
- **주석은 "왜"를 적는다.** 무엇을 하는지는 코드가 말하게 한다.
- 매직 넘버 · 매직 문자열은 이름 있는 상수로 (예: `RESEND_INTERVAL_SECONDS = 60`), 가능하면 외부 설정과 같은 값임을 적는다.
- 오류는 **삼키지 않는다.** 사용자에게 보여줄 문구 키로 바꾸거나, 기록하고 알린다.
- 타입으로 잘못된 상태를 막는다 (예: 선택 전 값은 `null`, 문자열 대신 유니온 타입).
