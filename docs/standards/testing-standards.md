# 테스트 기준

**무엇을 · 언제 · 어떤 종류로** 테스트하는지 정한다. 프로젝트 이름에 기대지 않게 쓴다.
코드를 **테스트할 수 있게 만드는 법**(계층별 구조, 순수 함수, 가짜 응답)은 [code-standards.md](code-standards.md) 3번에 있고, 여기서는 반복하지 않는다.
도구 이름은 기본값이다 (JS/TS 웹 프로젝트 기준). 버전 · 설치 · 주의점은 [tech-stack.md](tech-stack.md) "테스트 · 품질"을 본다.

## 1. 무엇을 반드시 테스트하나

| 대상 | 테스트 종류 | 필수 여부 | 기본 도구 |
|---|---|---|---|
| **계산 로직** (규칙 · 점수 · 날짜 · 변환 · 문장 조합 등 도메인 계산) | 단위 테스트 | **반드시 함께 올린다** | Vitest |
| 서비스 모듈 (외부 호출 결과 변환 · 오류 매핑) | 단위 테스트 (외부 응답은 가짜로) | 권장 | Vitest |
| 컴포넌트 | 컴포넌트 테스트 (상태별) | 새 공용 부품은 필수 ([code-standards.md](code-standards.md) 5번) | Testing Library + Vitest |
| **핵심 사용자 흐름** (가입 · 로그인 · 핵심 기능 한 바퀴 등) | E2E | 흐름마다 하나 이상 | Playwright |

- 계산 로직은 틀려도 화면에 바로 드러나지 않는다 → 코드와 **같은 PR에** 테스트를 올린다. 테스트 없는 계산 로직 PR은 머지하지 않는다.
- 버그를 고치면 **그 버그를 재현하는 테스트를 먼저** 더한다 → 같은 버그가 다시 나오지 않는다.

## 2. 파일 위치 · 이름

| 종류 | 위치 | 예 |
|---|---|---|
| 단위 · 컴포넌트 테스트 | 대상 파일 **바로 옆**에 `*.test.ts(x)` | `src/lib/date/day-boundary.ts` ↔ `day-boundary.test.ts` |
| E2E | 저장소 루트 `e2e/` | `e2e/signup.spec.ts` |

- 옆에 두면 대상을 옮기거나 지울 때 테스트가 같이 따라간다.
- 컴포넌트 테스트 파일은 맨 위에 `// @vitest-environment jsdom`을 적는다 (기본 환경은 node로 두고, 브라우저가 필요한 파일만 jsdom).
- 테스트 이름은 **무엇을 보장하는지** 문장으로 쓴다 ([code-standards.md](code-standards.md) 3번).

## 3. E2E 기준

- **모바일 뷰포트 기준**으로 돌린다 (기본 390px). 모바일에서 먼저 쓰이는 서비스가 많고, 좁은 화면에서 깨지는 곳이 더 많다. PC 전용 동작이 있으면 PC 뷰포트 케이스를 더한다.
- 외부 서비스(인증 · DB · LLM · 결제)는 **네트워크 단에서 가짜 응답**으로 바꾼다 (예: Playwright `page.route`). 실제 계정 · 비용 · 속도 제한에 기대지 않는다.
- 핵심 흐름만 E2E로 덮는다. 세부 분기는 단위 · 컴포넌트 테스트에서 확인한다 (E2E는 느리고 깨지기 쉽다).

## 4. PR 올리기 전

아래가 **모두 통과해야** PR을 올린다. CI도 같은 것을 돌리고, 통과해야 머지한다 ([git-workflow.md](git-workflow.md) 1번).

| 확인 | 예 (npm 프로젝트) |
|---|---|
| 단위 · 컴포넌트 테스트 | `npm test` |
| E2E (화면 · 흐름을 바꿨을 때) | `npm run test:e2e` |
| 타입 검사 | `npm run typecheck` |
| 린트 | `npm run lint` |
| 빌드 | `npm run build` |

- 실행하지 못한 확인이 있으면 PR에 **실행하지 못했다고** 적는다 ([working-principles.md](working-principles.md) 2번).
- 실패한 테스트를 건너뛰기(`skip`)로 넘기지 않는다. 꼭 필요하면 이유와 후속 이슈를 PR에 적는다.
